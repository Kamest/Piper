Piper and the other ways to run agents in parallel.

Many tools now run several coding agents side by side. They differ most in two things: what keeps one agent away from the rest of your machine, and when a person is asked. This page lays that out, with a source for each claim.

Checked on 2026-10-24 against each project's own site, docs and repository. Tools change quickly; tell us when something here is out of date.

In short

  • Isolation. Most local workspaces give each agent a git worktree. That keeps the files of parallel tasks apart, but the agent still runs as you, with your shell, network and credentials. Piper runs each session in a container (hole) that sees its project, not your home directory, with outbound traffic filtered.
  • Asking at the right moment. The tools we checked either ask about tool calls in general or not at all. Piper asks about specific actions: a push, production data, another project's files, an unknown HTTP host. Each action is a switch you can turn off.
  • Your machine, your subscription. Like most local workspaces, Piper drives the official Claude Code and Codex CLIs with your own account. Nothing runs in someone else's cloud.
  • Trade-offs. Piper needs Docker and builds a sandbox image on the first start, which takes minutes. It supports two agents, not twenty. It is a young 0.x project.

Hosted agents

Claude Code on the web, Codex cloud and Cursor's cloud agents run each task in a VM or container in the vendor's cloud. They isolate well and you can close your laptop. In exchange, your code and the credentials the task needs live in that cloud, network access is set per environment, and the work counts against your plan.

  • Claude Code on the web: an isolated VM per task, network None, Trusted, Full or Custom, and git through a proxy that keeps credentials out of the VM. The proxy refuses branch deletion and tag pushes but does not limit which branch is pushed. docs, environments
  • Codex cloud: containers, internet off by default for the agent, with an allowlist and an option to allow only GET, HEAD and OPTIONS. docs
  • Cursor cloud agents: isolated VMs with egress restrictions. docs

Pick one of these when the work fits a fresh clone in the cloud. Pick Piper when the work needs your local projects, databases, tunnels or tools, and you want to see and approve the moments that leave the sandbox.

The agents' own sandboxes

Both CLIs Piper runs have a sandbox of their own. Piper does not replace them; it adds a container boundary around the whole session and asks about actions inside the project's workflow.

  • Claude Code can sandbox its Bash commands (Seatbelt on macOS, bubblewrap on Linux and WSL 2) with a network allowlist. It is off by default, and its docs call it not a complete isolation boundary. docs
  • Codex CLI runs in workspace-write with the network off by default, and in on-request mode asks before writing outside the workspace or using the network. docs

On their own, these are good for one agent in one repository. They know nothing about a push to production versus a push to a feature branch, other projects, or which databases are production.

When Piper is not the right pick

  • You want agents other than Claude Code and Codex. Orca, Emdash and Superset support many more.
  • You cannot run Docker, or need native Windows without WSL 2.
  • You want tasks to keep running with your laptop closed. Use a hosted agent, or run Piper on a machine that stays on and reach it over your tailnet.
  • You need a mature, widely used tool. Piper is a 0.x release with a small team; the open checks are listed publicly.
